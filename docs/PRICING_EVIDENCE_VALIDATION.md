# iPhone Cashify evidence: held-out validation

Generated by `scripts/pricing-evidence/render_validation_report.py` from `data/pricing-evidence/validation/` (produced by `validate-evidence-engine.ts`). The existing and the evidence-calibrated engine are scored on **exactly the same held-out Cashify quotes**.

**How to read the numbers.** Error = the engine's Cashify-equivalent minus the observed Cashify *base price* (headline selling price + ₹20; the same basis as Cashify's Get Upto, which is the reference the engine starts from). Positive = the engine quotes above Cashify, which is the costly direction because Fhoneify's uplift sits on top. 'Existing engine' is today's `priceDevice` path with the form's current warranty-voiding rule; 'evidence engine' is `appleCashifyModel` refitted without the test rows; 'evidence + fallback' prices anything the evidence engine will not price with the existing engine, which is what production would do.

**Honest limits.**
- The *structure* of the model (age applied once, largest-wins groups, fixed versus proportional values, floors) was found by studying the whole dataset, including rows that later serve as test rows. The held-out protocols are honest about parameter estimation (no test row informs a fitted number) but optimistic about structure. The genuinely blind test is the next collection round (see `PRICING_EVIDENCE_NEXT_QUOTES.md`) against the thresholds fixed below.
- Most of the dataset replicates ~30 condition shapes across storages and models, so effective sample sizes are far smaller than row counts: protocol 1 holds out whole shapes for that reason.
- The calibration was fitted on Cashify quotes dated 16-24 Oct 2026. Nothing here shows the rules stay stable as Cashify changes its tables.

## Scope decision (protocols 1 and 2 pooled, held-out rows only)

Thresholds, fixed before the per-model numbers were read and applied identically to every model:

| # | threshold | why |
|---|---|---|
| T1 | median relative error <= 1.0% | most quotes should be indistinguishable from Cashify's own rounding and day-to-day movement (the Get Upto itself moved ~1% in a week) |
| T2 | 90th-percentile relative error <= 5% | a typical bad case is still a small share of the price |
| T3 | 95th-percentile OVER-quote <= 3% | quoting above Cashify is the costly direction: the uplift (up to 8%) sits on top, and the owner's ceiling is defined against the true Cashify payout |
| T4 | mean absolute error <= 50% of the existing engine's on the same rows | it must be clearly better, not marginally |
| T5 | >= 100 held-out quotes covering >= 10 distinct condition shapes (model level); >= 30 quotes over >= 5 shapes for the measured/inferred subsets (T5s) | otherwise there is not enough evidence to judge. The subset floor is lower than the model floor and is a judgement call to approve |
| T6 | declined (inspection/unsupported) share <= 15% | an engine that refuses most requests is not an engine |
| T7 | worst single over-quote <= 10% of that day's Get Upto | percentiles alone can hide one very large over-quote |

Relative error = |engine - Cashify base| / max(Cashify base, 20% of that day's Get Upto), so a floor quote of a few thousand rupees is not judged against itself.
